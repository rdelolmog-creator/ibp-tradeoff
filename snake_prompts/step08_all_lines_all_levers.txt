Step 8 of the §5 build order (D-046, architecture A-03): src/engine.py is
BROADENED, not rewritten. It already handles any lever combination on any

What is genuinely new here, and why it matters: every result so far has moved
ONE lever at a time (Step 6 gate, Step 7 sweep). Step 8 moves all FOUR
together, across all FOUR lines, which is the first point interactions become
visible — does a tight cover setting plus a large min_run_hours push a line
into overtime? Does a lever's effect on one line generalise to the others?

This run is ALSO the evidence O-10's review has been waiting for (D-063): does
any line breach capacity under realistic lever settings, or does the current
static SKU-to-line allocation hold up in practice? The O-10 review happens
immediately after this step, using this run's output.

No new parameters, no new mechanisms, no scope expansion. Grid, run, report.

In src/portfolio_sweep.py:

  def lever_grid(assumptions, n=4) -> dict[str, list[float]]
      Four values per lever, endpoints and midpoints from
      assumptions.levers.*.range. Same principle as Step 7's default_grid — no
      literals, everything read from config.

  def sweep_all_lines_all_levers(engine, grid) -> pd.DataFrame
      Full factorial over the four levers, run on every line in
      engine.line_master. One row per (line_id, service_target,
      inventory_cover_weeks, forecast_bias_correction, min_run_hours) with the
      four economic outputs, total_economic_cost_eur, service_achieved,
      utilisation_mean, and per-month max utilisation and overtime_hours (the
      O-10 evidence — a mean can hide a peak that breaches capacity).

      Use each line's own category default for forecast_bias_correction's
      flagged-SKU handling — this already lives in TradeOffEngine, do not
      reimplement it.

  def portfolio_summary(sweep) -> pd.DataFrame
      One row per line: best total_economic_cost_eur found, the lever setting
      that achieves it, worst-case utilisation and overtime_hours across the
      WHOLE grid (not just at the optimum — O-10 needs to know whether ANY
      realistic setting breaches capacity, not only the cheapest one), and
      whether an interior optimum exists per lever (same test as Step 7:
      optimum not at a grid edge).

  def lever_consistency(sweep) -> pd.DataFrame
      For each lever, holding the other three at each line's default: does the
      lever move each output in the SAME direction on every line, or does the
      direction flip? This directly tests whether Step 6/7's single-line
      findings generalise — in particular D-059 (bias lever says "don't
      correct" on L3) and the service-target dominance seen in Step 7's
      boundary optima.

TESTS — tests/test_portfolio_sweep.py:

  test_sweep_covers_every_line
  test_engine_is_not_modified

  test_lever_consistency_flags_direction_changes
      construct a case (synthetic assumptions, not the real pipeline) where a
      lever provably flips direction between two lines, and assert the
      function reports it — this function's whole job is not to miss that.
  test_ground_truth_not_importable
