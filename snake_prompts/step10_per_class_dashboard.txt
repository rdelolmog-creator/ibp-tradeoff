A — ACTION TO PERFORM

In src/app_logic.py — full rewrite, no `import streamlit`:

  base_levers_for_line(engine, assumptions, line_id) -> LeverSettings
      TRUE per-class default (LeverSettings.defaults_per_class()) — each
      class at its OWN default, not class A applied to everyone. This is
      what "Base" means now, matching Step 7/9's redefinition.

  optimal_levers_for_line(line_results, line_id) -> LeverSettings
      Reads the committed, capacity-verified optimum for ONE line. Not
      generalised to multi-line — different lines have independently-found
      optima, so the app disables "jump to optimal" when more than one line
      is selected rather than picking one arbitrarily.

  run_scenario_for_lines(engine, line_ids, levers, assumptions, schema) -> dict
      THE core function. Runs ONE per-class LeverSettings across every
      selected line — genuinely live, not cached or precomputed. Returns the
      combined avoidable-cost view (summed across lines, since SKUs never
      overlap between lines), the concatenated per-SKU sku_month, and a
      per-line capacity read.

  live_capacity_warnings(capacity_df) -> list[str]
      Computed from the scenario JUST run, not a static Step 8 lookup — the
      whole reason this module was rebuilt. A line is flagged only if the
      exact combination of levers currently on screen produced a real
      shortfall.

  by_class_breakdown(sku_month, levers) -> pd.DataFrame
      Aggregates sku_month (which arrives as one row per SKU PER MONTH) to
      one row per SKU first, THEN groups by class — a coarser aggregation
      would count SKU-months as SKUs. Conversion cost is not split per class
      (D-066); shown as pd.NA in this table, not fabricated.

  owner_table, line_policy_table: thin wrappers around src.reporter's
  equivalents, unchanged in spirit from the prior app_logic.

In app.py:

  Multi-select line picker (button-pills, not a dropdown) — "All lines" plus
  one button per line, toggle behaviour matching the validated mockup.

  "Jump to base" / "Jump to optimal" buttons set every slider via
  st.session_state, then the normal slider flow resumes on the next
  interaction — not a locked preset.

  Twelve sliders: one card per ABC class (A/B/C), four levers each
  (service_target, inventory_cover_weeks, forecast_bias_correction,
  min_run_hours), all bounds read from assumptions.levers.*.range.

  Cost bridge as a table: Base, Scenario, Δ vs base, and — only when exactly
  one line is selected — Δ vs optimal and Optimal. The optimal row is
  omitted, not faked, for a multi-line selection, with a caption explaining
  why (each line's optimum was found independently).

  Live capacity warnings shown as st.warning banners, computed on every
  rerun from whatever levers are currently set.

  By-class breakdown table, owner table, SKU detail table (one row per SKU,
  every column derived from the live scenario or the current lever values —
  no static data).

  Portfolio evidence section at the bottom: Step 7's line_policy_table and
  Step 8's lever-consistency table, both clearly labelled as reference,
  dated by their assumption fingerprint, not live.
