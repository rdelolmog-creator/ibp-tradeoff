RUNTIME BUDGET, stated up front because it drives the scope decision below:
a full joint search over cover x service, 3 classes, n=3 values each, is
3^6 = 729 combinations. A single run_scenario() call is ~63ms (measured,

is the ceiling the search design below is built to respect.

A — ACTION TO PERFORM
-------------------------------------------------------------------------------

SCOPE DECISION, stated explicitly rather than silently narrowed:
this search jointly optimises inventory_cover_weeks and service_target PER
CLASS (the two levers whose per-SKU-isolated treatment was the actual defect
found and retracted in D-071). forecast_bias_correction and min_run_hours are
held at fixed scalars DURING THE SEARCH — not because the engine can't do
per-class values for them (it can, as of D-071's Step 6 change), but because
searching all four levers per class simultaneously is 3^12 combinations,
computationally infeasible in the remaining time for marginal expected
benefit: cover is what drives batch size and therefore aggregate workload,
which is where the capacity-feasibility bug actually lived. Widening the
search to all four levers per class is a legitimate future extension, not
attempted here.

In src/policy_model.py:

  def joint_policy_grid(assumptions, n=3) -> tuple[list[float], list[float]]
      n values per lever from assumptions.levers.*.range — same principle as
      every prior grid, no literals.

  def search_joint_policy(
      engine, line_id, cover_values, service_values,
      bias_correction=0.0, min_run_hours=None
  ) -> pd.DataFrame
      Full factorial over (cover_A, cover_B, cover_C, service_A, service_B,
      service_C) — 3^6 combinations at n=3. min_run_hours defaults to the
      line's category default (read from config, not a literal) if not
      given; bias_correction defaults to 0.0. EACH combination is ONE REAL
      run_scenario() call with a full per-class LeverSettings — this is the
      entire fix: every candidate is genuinely, jointly simulated, so its
      capacity_shortfall_total is the TRUE aggregate answer for that exact
      combination, not an inference from separate runs.
      Returns one row per combination: the six per-class lever values, all
      four economic outputs, total_economic_cost_eur,
      capacity_shortfall_total, and utilisation_max.

  def best_feasible_policy(search_result) -> pd.Series
      FILTERS to capacity_shortfall_total <= 1e-6 first, THEN picks the
      minimum total_economic_cost_eur among the feasible rows. This ordering
      is the whole point: infeasible-but-cheap combinations are never
      eligible, so whatever this returns is a plan that could actually run.
      Raises PolicyModelViolation if NO row in the search is feasible — that
      is itself a finding (the grid's range cannot satisfy capacity anywhere)
      and must not be silently swallowed by returning the least-bad
      infeasible point.

  def search_all_lines(engine, n=3, bias_correction=0.0) -> pd.DataFrame
      Runs search_joint_policy + best_feasible_policy for every line, using
      each line's own category default for min_run_hours. Returns one row per
      line: the winning per-class cover/service values, the four outputs,
      total cost, and a `default_total_cost_eur` column for comparison — the
      default being each line's UNIFORM class-blind policy (today's
      LeverSettings.defaults(), scalar, class "A"), evaluated once as the
      baseline every optimum is measured against. saving_eur = default - best.

  def expand_to_sku_level(line_results, engine) -> pd.DataFrame
      For each line's winning combination, re-reads that ALREADY-COMPUTED
      scenario's sku_month (do not re-simulate — the winning row's per-SKU
      lost_sales_eur / excess_obsolescence_eur / working_capital_cost_eur
      come directly from the one joint simulation that produced it). Every
      SKU in a class inherits that class's chosen cover/service — this is not
      an approximation, it is what "policy set by class" means. Conversion
      cost is NOT split per SKU here — it stays a line total, displayed
      separately, labelled as such (D-066's finding that it isn't separable
      per SKU still holds; the difference is this file no longer PRETENDS a
      per-SKU split is a policy result). Output: sku_id, line_id, abc_class,
      cover_weeks, service_target (both inherited from the line's winning
      combination), lost_sales_eur, excess_obsolescence_eur,
      working_capital_cost_eur, line_conversion_cost_eur (repeated per SKU on
      that line, explicitly labelled a line total not a per-SKU figure).

PolicyModel (the ML fitting class) is updated to consume
expand_to_sku_level()'s output instead of the old optimise_all_lines() output.
Expect and REPORT plainly, not hide: with policy now set at class level, the
target values cluster into at most 3 x 4 = 12 distinct (cover, service) pairs
across 60 SKUs. SHAP finding abc_class as the dominant driver (already true in
the original Step 7 run) is now the EXPECTED, mechanistically correct result,
not a surprising one — the model is very nearly recovering class membership
because policy is, by this design, set by class. State this plainly in the
notebook rather than treating it as a weak result to explain away.
